# Security Policy

This document describes how to responsibly report security vulnerabilities in Audityzer and how the project handles them.

## Scope

This policy applies to:
- source code in this repository
- GitHub workflows and automation
- CI/CD configuration
- deployment scripts and environment setup
- dependencies and third-party integrations
- audit reports and operational artifacts generated by the project

## Reporting a vulnerability

Please do not open a public GitHub issue for security vulnerabilities.

Instead, report the issue privately using one of the approved channels:
- GitHub Security Advisories (preferred, if enabled for this repository)
- a private email address maintained by the project owners
- a private maintainer channel approved for security reporting

When reporting, include:
- a summary of the vulnerability
- affected component or file
- version or branch information
- reproduction steps
- impact assessment
- any relevant logs, screenshots, or proof-of-concept
- suggested remediation if known

## Response expectations

We aim to acknowledge security reports within 5 business days.

After triage, the maintainers will:
- validate the report
- assess severity and impact
- prioritize remediation
- coordinate a fix and disclosure timeline

We will do our best to keep reporters informed throughout the process.

## Severity handling

We prioritize vulnerabilities based on impact and exploitability:

- Critical: remote code execution, authentication bypass, secret leakage, severe supply-chain compromise
- High: privilege escalation, significant data exposure, widespread integrity risk
- Medium: moderate attack complexity or limited impact
- Low: minor security weakness with limited exploitation potential

The expected remediation timeline depends on severity, but critical issues will be treated as urgent.

## Disclosure policy

We ask reporters to keep vulnerability details private until:
- a fix is available, or
- the maintainers explicitly authorize disclosure

Public disclosure without prior coordination may increase risk and reduce the effectiveness of remediation. We support responsible disclosure.

## Security responsibilities for contributors

All contributors must:
- never commit secrets, API tokens, private keys, or credentials
- never expose production configuration in code, logs, issues, or PRs
- avoid introducing vulnerable dependencies
- review workflow and automation changes carefully
- use least-privilege principles for GitHub permissions and automation
- report suspicious or unsafe behavior immediately

## Required review for sensitive changes

Changes affecting any of the following must be reviewed by a maintainer before merge:
- authentication or authorization logic
- secrets or environment variables
- GitHub Actions or CI/CD workflows
- external integrations or API clients
- dependency updates with security implications
- infrastructure configuration
- data handling, storage, or reporting workflows

## Secure development expectations

This project follows a secure-by-default model:
- branch protection is required for protected branches
- code review is required for sensitive changes
- permissions must be restricted to the minimum required
- automation must be approved before execution
- workflows must not print or log secrets
- automation must not write beyond the triggering resource without explicit approval

## Supported versions

The maintainers support the latest version on the default branch and the most recent release branch. Security fixes are prioritized for actively supported versions.

## Safe use of automation

AI-assisted tooling, GitHub Actions, and automation must:
- use the least-privilege permissions model
- require explicit approval before privileged execution
- avoid broad repository access by default
- not expose secrets in prompts, logs, issues, or artifacts
- be reviewed and audited before merge

## Handling suspected abuse

If abuse, malicious automation, or a credential leak is detected:
- revoke or disable the affected access immediately
- review logs and workflows
- rotate exposed credentials
- notify maintainers and relevant stakeholders
- document the issue and remediation plan

## Responsible disclosure statement

We appreciate responsible disclosure and recognize that security researchers and contributors play an important role in improving the project.

If a report is made in good faith and follows this policy, the maintainers will treat it as a constructive contribution to the project’s security posture.

## Contact

For private security reports, please use the repository’s GitHub private security reporting channel or the project’s designated secure contact method.

If no private contact is available, please contact the maintainers through the official repository owner or organization channels and clearly label the message as a security report.
